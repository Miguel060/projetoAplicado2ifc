# 04.01 — Frontend project setup

## Goal

A `frontend/` folder holding a **React 19 + Vite 8 + TypeScript 7 (strict)**
single-page app styled with **Tailwind CSS 4** and **shadcn/ui**, which:

- builds to static files in `frontend/dist/` (uploaded by `deploy.yml`);
- reads data **only** from `/data/...` on its own origin;
- in development, serves the ETL output (`backend/dist/data`) at `/data`
  without copying it anywhere;
- respects the production Content Security Policy (no inline scripts, no
  third-party origins);
- carries its tests from the first commit: Vitest + Testing Library for unit
  and component tests (coverage ≥ 85 %), Playwright + axe for end-to-end
  tests against the production build (`01-foundation/05-testing-strategy.md`,
  D15). The whole test approach is in `08-testing.md`.

The versions below are a set already proven to work together
(`00-overview/04-tech-stack.md`). Pin them exactly.

## Step 3 — `vite.config.ts`: data middleware + Vitest

```ts
import { createReadStream, statSync } from "node:fs";
import path from "node:path";
import { fileURLToPath } from "node:url";
import tailwindcss from "@tailwindcss/vite";
import react from "@vitejs/plugin-react";
import type { Connect, Plugin } from "vite";
import { defineConfig } from "vitest/config";

/**
 * Where /data is served from, outside production:
 * - default: the local ETL output (`make ingest`) — for `npm run dev` / `npm run preview`;
 * - E2E_DATA_DIR: set by playwright.config.ts to the backend's committed golden
 *   snapshot (../backend/testdata/golden/data), so end-to-end tests run against
 *   the backend's real output.
 * Neither is ever copied into the build.
 */
const LOCAL_DATA_DIR = process.env["E2E_DATA_DIR"]
  ? path.resolve(process.env["E2E_DATA_DIR"])
  : fileURLToPath(new URL("../backend/dist/data", import.meta.url));

/**
 * Optional: point the dev server at a deployed snapshot instead of a local ETL
 * run, e.g. DATA_PROXY_TARGET=https://dxxxxxxxx.cloudfront.net npm run dev.
 * Lets someone work on the UI without installing Go.
 */
const DATA_PROXY_TARGET = process.env["DATA_PROXY_TARGET"];

const CONTENT_TYPES: Record<string, string> = {
  ".json": "application/json; charset=utf-8",
  ".jpg": "image/jpeg",
  ".jpeg": "image/jpeg",
  ".sqlite": "application/vnd.sqlite3",
};

/** Serves LOCAL_DATA_DIR at /data with real 404s, like the CloudFront setup. */
function localData(): Connect.NextHandleFunction {
  return (req, res) => {
    const urlPath = decodeURIComponent((req.url ?? "/").split("?")[0] ?? "/");
    const filePath = path.join(LOCAL_DATA_DIR, urlPath);
    // Refuse path traversal (`/data/../../etc/passwd`).
    if (!filePath.startsWith(LOCAL_DATA_DIR + path.sep)) {
      res.statusCode = 403;
      res.end();
      return;
    }
    let isFile = false;
    try {
      isFile = statSync(filePath).isFile();
    } catch {
      isFile = false;
    }
    if (!isFile) {
      // A real 404 — never fall back to index.html for data paths.
      res.statusCode = 404;
      res.end("Not found");
      return;
    }
    const type = CONTENT_TYPES[path.extname(filePath)] ?? "application/octet-stream";
    res.setHeader("Content-Type", type);
    res.setHeader("Cache-Control", "no-store");
    createReadStream(filePath).pipe(res);
  };
}

function serveLocalData(): Plugin {
  return {
    name: "serve-local-data",
    // configureServer runs for `vite`, configurePreviewServer for `vite preview`
    // (which is what Playwright starts). `vite build` calls neither hook, so the
    // middleware never reaches production.
    configureServer(server) {
      if (!DATA_PROXY_TARGET) server.middlewares.use("/data", localData());
    },
    configurePreviewServer(server) {
      if (!DATA_PROXY_TARGET) server.middlewares.use("/data", localData());
    },
  };
}

const proxy = DATA_PROXY_TARGET
  ? { "/data": { target: DATA_PROXY_TARGET, changeOrigin: true } }
  : undefined;

export default defineConfig({
  plugins: [react(), tailwindcss(), serveLocalData()],
  resolve: {
    alias: { "@": fileURLToPath(new URL("./src", import.meta.url)) },
  },
  server: { port: 5173, strictPort: true, ...(proxy ? { proxy } : {}) },
  preview: { port: 4173, strictPort: true, ...(proxy ? { proxy } : {}) },
  build: {
    target: "es2022",
    sourcemap: true,
    // Keep everything as files: no inlined assets as data: URIs except tiny ones.
    assetsInlineLimit: 0,
  },
  test: {
    environment: "jsdom",
    setupFiles: ["./src/test/setup.ts"],
    include: ["src/**/*.test.{ts,tsx}"],
    restoreMocks: true,
    coverage: {
      provider: "v8",
      include: ["src/**/*.{ts,tsx}"],
      // Exactly the exclusions allowed by 01-foundation/05-testing-strategy.md:
      // generated shadcn components, the entry point, type declarations, and
      // test code itself (test files + src/test/ helpers).
      exclude: [
        "src/components/ui/**",
        "src/main.tsx",
        "**/*.d.ts",
        "src/**/*.test.{ts,tsx}",
        "src/test/**",
      ],
      thresholds: { lines: 85, statements: 85, functions: 85, branches: 85 },
      reporter: ["text-summary", "html", "lcov"],
      reportsDirectory: "./coverage",
    },
  },
});
```

`defineConfig` is imported from `"vitest/config"` (same signature as Vite's,
plus the `test` key) — the pattern already proven with this Vite/Vitest
pairing.

## Step 3b — `playwright.config.ts`

```ts
import { defineConfig, devices } from "@playwright/test";

/** Fixed port, different from `npm run preview` (4173), so a manual preview can stay open. */
const PORT = 4317;
const CI = Boolean(process.env["CI"]);

export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  forbidOnly: CI,
  retries: CI ? 2 : 0,
  workers: CI ? 2 : undefined,
  reporter: CI ? [["github"], ["html", { open: "never" }]] : [["list"], ["html", { open: "never" }]],
  use: {
    baseURL: `http://localhost:${PORT}`,
    locale: "pt-BR",
    timezoneId: "America/Sao_Paulo",
    trace: "retain-on-failure",
    screenshot: "only-on-failure",
  },
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
    { name: "webkit", use: { ...devices["iPhone 13"] } },
  ],
  webServer: {
    // The production build, exactly what deploy.yml uploads.
    command: `npm run build && npx vite preview --port ${PORT} --strictPort`,
    url: `http://localhost:${PORT}`,
    reuseExistingServer: !CI,
    timeout: 120_000,
    env: { E2E_DATA_DIR: "../backend/testdata/golden/data" },
  },
});
```

- **Production build, not the dev server:** the dev server injects inline
  scripts and serves untransformed modules; only the build is what users get.
- **Golden snapshot at `/data`:** the preview middleware serves
  `backend/testdata/golden/data` (committed by the backend's pipeline test).
  Until that folder exists (before the TSE snapshot step), every `/data`
  request answers 404 — which is exactly the "no data yet" scenario the
  landing page must survive. Specs that need other data use `page.route`
  (see `08-testing.md`).
- `locale` and `timezoneId` make dates render as they will for Brazilian
  visitors, on any CI runner.

### Why not put the data in `public/`?

- Everything in `public/` is **copied into `dist/`** on build, so the site
  deploy would upload a stale data snapshot together with the app. Data has
  its own pipeline (`refresh-data.yml`) and its own versioned paths; mixing
  them would let a site deploy overwrite or contradict the live data.
- The site deploy runs `aws s3 sync … --delete --exclude "data/*"`; files
  under `dist/data/` would fight that exclusion.
- `public/` files get the site's cache headers, not the data's (immutable
  versions + short-lived `latest.json`).
- Photos and the SQLite file would bloat every frontend build.

`assetsInlineLimit: 0` keeps fonts and images as same-origin files instead of
`data:` URIs, which keeps the CSP simple (`font-src 'self'`).

## Step 6 — Tailwind 4 + design tokens (`src/index.css`)

Rules for the palette:

- **Neutral only.** Greys for surfaces and text, one neutral dark "primary"
  for buttons and focus. **No party colours**, no green/red for elected/not
  elected (colour must never carry meaning — see `07-…-neutrality.md`).
- **WCAG AA contrast:** body text ≥ 4.5:1, large text and non-text UI
  (input borders, focus ring, bars) ≥ 3:1 against their background.
- **Light theme is mandatory.** Dark is optional and, if shipped, follows the
  OS setting via media query (no toggle, no script).

shadcn's default neutral tokens fail two checks and must be adjusted:
`--border`/`--input` at `oklch(0.922 0 0)` are ~1.3:1 on white (an input
border must be ≥ 3:1, WCAG 1.4.11), and `--muted-foreground` at
`oklch(0.556 0 0)` passes 4.5:1 only barely. The values below fix both.

  return (

## Step 8 — CSP compatibility constraints (production)

CloudFront adds the Content Security Policy as a response header
(`05-infrastructure/`). The policy is:

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
frame-ancestors 'none'
```

What each directive means for the frontend code:

| Directive | Value | Consequence for the code |
|---|---|---|
| `default-src` | `'self'` | Anything not listed below is same-origin only. |
| `script-src` | `'self'` — **no** `'unsafe-inline'`, **no** `'unsafe-eval'` | No inline `<script>` in `index.html` (hence no pre-paint theme script — Step 4), no `eval`/`new Function`, no third-party scripts (analytics, widgets, embeds). Vite's production build emits only external module scripts, so it complies. |
| `style-src` | `'self' 'unsafe-inline'` | Bundled CSS files **and** `<style>` elements injected at run time. See "Why `'unsafe-inline'` for styles" below. |
| `img-src` | `'self' data:` | Photos come from `/data/<version>/photos/`. The photo placeholder is an inline React SVG (no URL). `data:` covers small images a library may inline. |
| `font-src` | `'self'` | Inter is bundled by Vite into `dist/assets/`; no Google Fonts or other font CDN. |
| `connect-src` | `'self'` | Every `fetch` uses a relative `/data/...` URL. Never fetch an official source directly from the browser (`00-overview/02-decisions.md`, D6). |
| `frame-ancestors` | `'none'` | The site cannot be framed (clickjacking). Nothing to do in the app. |

### Why `'unsafe-inline'` for styles

Radix primitives used by shadcn/ui components (Select, Dialog, Popover and
others) lock page scrolling through `react-remove-scroll`, which uses
`react-style-singleton` to **inject a `<style>` tag at run time**. Without
`'unsafe-inline'` in `style-src`, the browser blocks that tag and the
component breaks subtly (the page scrolls behind an open overlay, layout
shifts). Allowing inline styles keeps any shadcn/ui component usable now or
later without a policy change.

The risk accepted is small: inline **styles** cannot execute code. The
dangerous part of an XSS — running script — stays blocked because
`script-src` has no `'unsafe-inline'` and no `'unsafe-eval'`. On top of that,
React escapes all text it renders, and the app never uses
`dangerouslySetInnerHTML`.

Notes:

- React `style={{ width }}` (used by `ValueBar`) is applied through the CSSOM
  and would work even without `'unsafe-inline'`; it is not the reason for it.
- External links (TSE, Câmara dos Deputados, social profiles) are plain
  `<a href>` navigation, which CSP does not restrict.
- The Vite dev server injects inline HMR scripts; that is fine because CSP is
  applied only by CloudFront in production. After the first deploy, open the
  deployed site → DevTools → Console: there must be **zero** CSP violation
  messages on every page type.
